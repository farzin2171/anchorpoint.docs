# PostgreSQL migration notes (T015)

Audience: a new engineer on the DIT identity platform program. Purpose: list every SQL Server specific
item in the source material so the new program (PostgreSQL only, Npgsql + EF Core) does not inherit it.
Feeds ADR-005 and research R6 (`specs/001-identity-platform-build/research.md`).

Scope of evidence: read-only grep and file reads of `C:\MyWork\stepwise_identity\src` (the "source
sample", EF Core 10.0.7, Duende IdentityServer 8.0.6) and of `C:\work\Applications.IdentityGateway`,
`C:\work\Services.User`, `C:\work\ACME.API.Middleware` (production references). Anything not directly
seen is marked "unverified".

## 0. Ground rules

1. The new program contains no SQL Server code, packages, scripts or containers.
2. **Migrations are regenerated from the model against Npgsql. Never port or edit the SQL Server
   migration files.** Every `Migrations` folder and `*ModelSnapshot.cs` listed below is reference only.
3. Column types (`nvarchar`, `datetime2`, `bit`, `uniqueidentifier`) appear in the SQL Server
   migrations and snapshots as `HasColumnType(...)`. They are generated output, not hand-written model
   code. In the source sample no `HasColumnType`, `HasDefaultValueSql`, `FromSqlRaw`, `ExecuteSqlRaw`,
   `RowVersion`, `[Timestamp]` or `IsolationLevel` appear in hand-written code (grep of `src`, excluding
   `Migrations`). The model is therefore mostly provider neutral, which makes regeneration cheap.
4. Source sample entity keys are mixed: `Guid` (Policy, PolicyChangeRequest, OutboxMessage, ProcessedEvent),
   `int` identity (Duende tables, `ExternalUserClaim`, connector tables) and `string` (Tenant key,
   `ExternalUser.SubjectId`). The new User Service model (`data-model.md`) uses UUID keys.

### 1.8 Regenerating the Duende stores for PostgreSQL

The Duende contexts are unmodified stock contexts in the source sample, so the schema comes from
the `Duende.IdentityServer.EntityFramework` package, not from the sample's migrations.

1. Configure Npgsql on both stores in the new Identity Server host
   (`AddConfigurationStore` and `AddOperationalStore`, `UseNpgsql(cs, o => o.MigrationsAssembly(...))`).
2. Create a design time factory or use the host as startup project, then run, once per context
   (names are Duende's; the migration folders are the host's choice):
   `dotnet ef migrations add Initial -c ConfigurationDbContext -o Data/Migrations/ConfigurationDb`
   `dotnet ef migrations add Initial -c PersistedGrantDbContext -o Data/Migrations/PersistedGrantDb`
3. Apply the snake_case convention (section 6) before generating, otherwise Duende tables come out
   PascalCase and quoted. Duende documents providing your own migrations; whether the Duende
   package ships PostgreSQL migrations is **unverified** and should not be assumed.
4. When Duende is upgraded, regenerate a new migration from the diff (the production repo does this
   with `build/is-generate-migration.ps1`, see section 2.1).
5. Verify the result with a Testcontainers test that runs `Migrate()` on an empty PostgreSQL and
   performs a token issuance.

|---|---|---|---|
| String comparison | default collation, case insensitive: `Key == tenantKey`, `ClientId`, `LIKE` | case sensitive `=` and `LIKE` | Normalise on write (lowercase) or `citext`; use `ILike` for patterns |

## 6. Proposed PostgreSQL naming and type conventions (feed for ADR-005)

| Topic | Proposal | Justification |
|---|---|---|
| Tables | `snake_case`, plural: `users`, `external_identities`, `roles`, `user_roles` | Unquoted lowercase identifiers need no quoting in hand written SQL or psql; research R6 and `data-model.md` already fix snake_case |
| Columns | `snake_case`: `display_name`, `is_active`, `provider_user_id`, `created_at`, `updated_at` | Matches the logical names already used in `data-model.md` |
| Duende tables | Apply the same naming convention globally so `clients`, `client_secrets`, `persisted_grants` etc. are snake_case; generated at migration time | One convention across contexts; Duende itself does not require PascalCase names (assumption, verify with the Initial migration test) |
| Keys / indexes / constraints | `pk_<table>`, `fk_<table>_<ref>`, `ix_<table>_<cols>`, `ux_<table>_<cols>`; keep under 63 bytes | PostgreSQL truncates identifiers over 63 bytes silently; the EF default `IX_<Table>_<col1>_<col2>...` can exceed it for composite indexes |
| Primary keys for app tables | `uuid`; generated in the app with `Guid.CreateVersion7()` (time ordered), no DB default needed | Replaces `NEWSEQUENTIALID()` (production IdG) without a DB function; v7 keeps btree locality. `gen_random_uuid()` is the fallback |
| Primary keys for Duende tables | keep Duende's `int` identity | Schema is Duende's (`data-model.md` Track I); changing key types is not supported by the stores |
| Strings | `text` for unbounded; `varchar(n)` only where a real limit is a business rule (`Role.key`, `Tenant.key`) | `nvarchar(max)` maps to `text`; PostgreSQL has no performance penalty for `text` and no 450 char index cap like SQL Server |
| Booleans | `boolean` | replaces `bit` |
| Timestamps | `timestamptz` everywhere, `DateTime` always `Kind=Utc` (or `DateTimeOffset`); columns named `*_at` | replaces `datetime2`; matches `data-model.md`; avoids Kind based Npgsql exceptions |
| Case sensitivity | Default `text` (case sensitive). Natural keys that humans type (role key, tenant key) stored lowercase and validated in the app. `citext` only if a decision requires insensitive matching; (`provider`, `provider_user_id`) stays case sensitive | SQL Server's case insensitive collation was implicit and unrecorded; the `Key == tenantKey` lookups and the CORS `Like` depend on it. Making it explicit avoids silent behavior change |
| Schema | default `public` per service database (each service its own database, constitution V) | The production `dbo` schema usage (`[dbo].[Users]`) disappears |
| Seed data | Through migrations only for static reference data, with fixed UUIDs; otherwise through the ingestion tool | Keeps `HasData` deterministic; avoids identity sequence drift |
| Migration history | `__ef_migrations_history` default, one context per database where possible | The source sample needed `__EFMigrationsHistory_Connectors` only because two contexts share one DB |
| Provider | `Npgsql.EntityFrameworkCore.PostgreSQL` matching the EF Core major version, PostgreSQL version pinned in docker-compose/Testcontainers and CI | Source sample is on EF Core 10.0.7, production on a `$(EntityFrameworkCoreVersion)` property (value unverified) |
