# Discovery: Mini vs production comparison (T012)

Read-only comparison between the "Mini" teaching solution and the three production repositories. It scopes this phase: Track C (shared library), Track U (User Service) and Track I (Identity Server).

## Sources and conventions

| Short name | Location (outside this repo) | Notes |
|---|---|---|
| Mini | `C:\MyWork\stepwise_identity\src\IdentityServerHost`, `Mini.UserService`, `Mini.Infrastructure` (plus `Mini.AcmeApi`, `Mini.AuthorizationService` for context) | net10.0, Duende 8.0.6, EF Core 10, SQL Server |
| IdG | `C:\work\Applications.IdentityGateway` | `src/Equisoft.IdentityGateway` targets net8.0; Duende version property `IdentityServerVersion` = 7.3.2 (`src/Equisoft.IdentityGateway/Equisoft.IdentityGateway.csproj`) |
| User | `C:\work\Services.User` | `src/UserService` targets net10.0 (`src/UserService/UserService.csproj`) |
| ACME MW | `C:\work\ACME.API.Middleware` | `src/AcmeMiddleware` targets net8.0 (`src/AcmeMiddleware/AcmeMiddleware.csproj`) |

Paths in the Production column are relative to the repo named in that column (IdG, User or ACME MW). Files outside this docs repo are cited with backticks, not links.

Target flow for this phase: Demo web app -> Identity Server (code + PKCE, external provider such as Entra ID) -> `IProfileService` calls User Service (client credentials, scope `user.read`) -> User Service calls the Tenant Middleware (tenant + groups) and merges its own roles -> claims `sub, name, email, role, group, tenant`.

Decisions already made (used as the yardstick for "Include"): fail closed at both hops; no profile caching at the Identity Server; unknown users refused (no auto-create); exactly one tenant per user in v1; user matched by (external provider, provider's stable user ID), never by email; tenants and groups in v1, fine-grained permissions deferred.

"Include" means: now = needed in Tracks C/U/I of this phase; later = a later phase or track; never = deliberately not rebuilt.

## 1. User, role and group model

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| Local user record in the Identity Server | `ExternalUser` keyed by a string subject `external:{scheme}:{externalSubjectId}` plus a generic `ExternalUserClaim` table (`IdentityServerHost/Data/UserDbContext.cs`) | `User` with GUID `Id`, `FirstName`, `LastName`, `Email`, `IsActive`, child `UserClaim` and `UserProvider` rows (IdG `src/Equisoft.IdentityGateway/Models/User.cs`, `UserClaim.cs`, `UserProvider.cs`) | now | Need an internal user with a stable ID and an `IsActive` flag. Mini has no `IsActive` and no real user columns. Where the user record lives (Identity Server vs User Service) is an open question below |
| Match key | Composite string built from scheme + provider subject (`IdentityServerHost/Controllers/ExternalController.cs`) | `UserProvider(ProviderName, ProviderSubjectId)`, looked up by `UserStore.FindByExternalProviderAsync` (IdG `src/Equisoft.IdentityGateway/Data/Stores/UserStore.cs`). Uniqueness is not a DB constraint (IdG `docs/context.md`, "Invariants") | now | Matches the decision (provider + stable ID, never email). Add a real unique index on (provider, provider user ID), which production lacks |
| Auto-provisioning on first login | `ExternalUserStore.ProvisionAsync` upserts on every login, unconditionally | `ExternalController.Callback` calls `AutoProvisionUserAsync` when no user is found (IdG `src/Equisoft.IdentityGateway/Modules/Account/ExternalController.cs`); no allow-list (IdG `docs/context.md`, "Landmines") | never | Decision: unknown users are refused. A refused login must still be audited |
| User deactivation | `IsActiveAsync` only checks that the user exists (`IdentityServerHost/Services/SampleProfileService.cs`) | `IsActiveAsync` returns `user?.IsActive == true` (IdG `src/Equisoft.IdentityGateway/IdentityServer/Services/EquisoftProfileService.cs`) | now | Needed so a disabled user stops getting tokens. Combined with "no caching" it takes effect immediately |
| Claims copied from the external provider onto the user at login | Only `name` and `tenant_id` are stored | Full claim set copied, remapped, and deleted/re-added on every login (`UserStore.SetClaims`, `UpdateInformationAsync`) | later | v1 needs only name and email. Copying arbitrary external claims into a table is what makes the production claim mapping complex. Keep a small fixed set, refreshed per login |
| Role source | One role per user: Mini.UserService table `UserIdentityRoles` (`Mini.UserService/Data/ServiceDbContext.cs`) or a per-tenant connector chain | One role string per user from the tenant's connector chain: Azure Graph app roles, a tenant WebApi, or a JWT claim (User `src/UserService.Services/V2/ActionHandlers/CascadingUserIdentityRoleHandler.cs`, `UserIdentityRoleHandler.cs`). Not stored in User Service (User `docs/context.md`, "Not responsible for") | now | Target needs roles owned by the User Service. Use a local table (like Mini) plus the Tenant Middleware, not a connector engine. The cascading connector engine is a later concern |
| Role vocabulary | Free string. Seeded `Admin`, fallback `Member` | Fixed code mapping `IDR_AGENT`, `IDR_MANAGING_AGENT`, `IDR_CLIENT`, `IDR_EMPLOYEE` to `Agent`, `ManagingAgent`, `Client`, `Employee` (User `src/UserService.Services/V2/Services/Mapper/IdentityRoleMapper.cs`); `Guest` is hard-set by IdG for guest logins (IdG `EquisoftTokenResponseGenerator.cs`) | later | These are insurance-domain roles. The new demo needs a small neutral set. Roles are data, not an enum in code |
| Multiple roles per user | Single role claim | Single role. The Graph connector keeps the alphabetically first role and logs a warning if several (User `docs/context.md`, "Critical flows" 2) | now | Target claim set has `role` (plural by nature). Return a list, not one winner. Production's "first alphabetical" rule loses information |
| Groups | Not modelled | No group claim is issued by IdG or User. ACME MW reads Entra group membership (`MemberOf`) but returns only the first group display name, as a "role" (ACME MW `src/AcmeMiddleware/Services/UserService.cs`) | now | Decision: groups are in v1. Source is the Tenant Middleware; the new User Service returns them as `group` claims. No production code to port, design is new |
| Fallback role when none found | `Member` returned for unknown user or empty chain (`Mini.UserService/Endpoints/UserEndpoints.cs`) | Role omitted from the token if the lookup fails or returns null (see section 4 for failure behavior) | never | A silent default role is fail-open. Decision is fail closed; no invented default |
| Local-id <-> external-id conversion | `GET /api/v2/useridentity/convert/{userId}` calls back into the Identity Server `UserConversionController` (`Mini.UserService/Endpoints/UserEndpoints.cs`) | Same two-way dependency: User `UserIdentityController` calls IdG `GET api/user/convert/{userId}` (User `src/UserService/V2/Controllers/UserIdentityController.cs`, IdG `src/Equisoft.IdentityGateway/Modules/User/UserController.cs`) | later | Exists for legacy consumers. A circular User <-> IdG dependency is something to avoid in the rebuild |

## 2. Claim mapping (which claims, from where)

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| `sub` | Local subject `external:{scheme}:{externalSubjectId}` (`IdentityServerHost/Controllers/ExternalController.cs`) | The local user GUID (`user.Id.ToString("D")`), not the external ID (IdG `Modules/Account/ExternalController.cs`) | now | Target `sub` must be an internal, opaque, stable ID. Mini's prefixed string leaks the provider |
| `name` | From the external principal's `name` | Mapped from `ClaimTypes.Name`, or built from given and family name; on several name claims it picks one at random (`new Random()` in `ExternalController.FindUserFromExternalProviderAsync`) | now | Take `name` from the provider claim deterministically. Do not copy the random pick |
| `email` | Not issued | Copied from the provider claims into `User.Email` and the `email` identity resource (IdG `config/identityResources.json`) | now | Target set includes `email`. Use it as display data only, never as the match key |
| `role` | Added by `SampleProfileService` from `UserClient.GetRoleAsync` | Claim is named `identityRole`, added in `EquisoftTokenResponseGenerator.AddIdentityRoleToPayloadAsync` using the external object ID (IdG `Models/Constants/CustomJwtClaimTypes.cs`) | now | Target claim name is `role`. Add it in the `IProfileService`, as Mini does, not in a token response generator |
| `group` | Not issued | Not issued | now | New claim. Multi-valued |
| `tenant` | `tenant_id` = friendly key (e.g. `acme`) and `tenant_guid` = GUID | `tenant` = key (from the scheme's `EcosystemTenant`) and `tenantId` = GUID added at token time (`CustomJwtClaimTypes.Tenant`, `TenantId`) | now | Target has one `tenant` claim. Decide key vs GUID: see open questions. Do not carry both |
| Where claims are assembled | `IProfileService.GetProfileDataAsync` (`IdentityServerHost/Services/SampleProfileService.cs`) | Split: profile service returns stored claims; token response generator injects tenant and role, mutating the subject principal (IdG `IdentityServer/ResponseHandling/EquisoftTokenResponseGenerator.cs`) | now | Target flow says `IProfileService`. One place, and it runs for userinfo and refresh too |
| Claim allow-list for token | Everything the profile service adds is requested via `AddRequestedClaims` | `AllowedUserExtraClaimTypes` = `tenantId`, `identityRole`; stored claims named `client_*`, `service_*` or those two are rejected at login (`VerifyForbiddenClaims`) | now | Claim-injection defense is cheap and valuable: an external provider must not be able to inject `role`, `group` or `tenant` |
| Provider-specific claim mapping | Not present | Per-provider `ClaimMappings` JSON on the provider record, applied before everything else (IdG `IdentityServer/Models/BaseIdentityProvider.cs`, `ApplyClaimMappings`) | later | v1 has one provider type (Entra ID). Hard-code the mapping first, make it configurable when a second provider appears |
| `externalobjectidentifier` claim | Not present | Provider subject kept as a claim, requested via its own identity resource (IdG `config/identityResources.json`); used as the User Service lookup key | later | In the target, the (provider, provider ID) pair lives in the user record, so no extra claim in tokens |
| Claims for service accounts | None | `client_` / `service_` prefixes with `service_tenant`, `service_isService` (IdG `config/clients.json`, `Models/Constants/CustomJwtClaimTypes.cs`) | now | Needed for the client-credentials hop: the User Service must tell a service caller from a user |

## 3. Tenant handling (resolution, registry, per-tenant configuration, connectors)

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| Tenant resolution at login | `TenantResolutionMiddleware` reads `acr_values=tenant:<name>` from the raw URL (`IdentityServerHost/TenantResolutionMiddleware.cs`) | Tenant is a property of the identity-provider scheme (`EcosystemTenant`), via `TenantAccessor` (IdG `Infrastructure/Tenant/TenantAccessor.cs`); `acr_values=tenant:` selects which schemes are offered and is mandatory unless the client sets `DisableTenantRequirement` (IdG `Configurations/Authentication/Helpers/AuthenticationHelper.cs`, `Configurations/Extensions/ClientExtensions.cs`) | now | One tenant per user in v1. Resolve the tenant from the user record, not from a request parameter, so a caller cannot choose its tenant. `acr_values` can remain a login hint only |
| Tenant registry | Hard-coded dictionary in the IdS (`IdentityServerHost/Tenants.cs`), plus a table in Mini.UserService (`Tenants`) and a third in MvcClient (drift acknowledged in `Mini.UserService/Endpoints/ManagementEndpoints.cs` comments) | External "Tenant Management" service, `GET {Address}/v1/tenants/GetByKey/{key}` via `TenantClient` (IdG `Data/Externals/Clients/TenantClient.cs`). Neither IdG nor User owns a registry (IdG `docs/context.md`; User `docs/context.md`) | now | The registry belongs outside the IdS. One owner only (the Tenant Middleware or the User Service, per open question), never a copy |
| Tenant lookup result | `tenant_guid` fetched via `TenantClient`; 404 aborts token issuance | Same call; result cached in `IDistributedCache` with `AbsoluteExpiration = DateTimeOffset.MaxValue` (IdG `EquisoftTokenResponseGenerator.cs`, `AddTenantIdToPayloadAsync`) | never | Never-expiring cache is a known bug reproduced on purpose in Mini. Decision: no caching at the IdS |
| Tenant deactivation | `IsActive` filter on read endpoint, breaks the next login (`Mini.UserService/Endpoints/TenantEndpoints.cs`) | Unverified in User/IdG (IdG `docs/context.md` does not say) | now | Needed for fail closed: an inactive tenant must not get tokens |
| Per-tenant identity providers | Providers in `appsettings` (`ExternalProviders` section) or in the `IdentityProviders` table; each declares `EcosystemTenant` (`IdentityServerHost/Configurations/Authentication/Helpers/AuthenticationHelper.cs`) | Same, plus per-client IdP allow-list written twice in `config/clients.json` (`Properties` CSV and `IdPRestrictions`; IdG `docs/context.md`) | later | v1 has one external provider. Per-tenant provider selection is needed once there are several tenants with different providers |
| Per-tenant connector configuration (role source) | `Mini.UserService/Connectors/*`: WebApi, Claim, plus cascading choice tables; Azure Graph pick present but disabled for one tenant | Tables `Connectors`, `ConnectorHandlerTenants`, `ConnectorHandlerCascadingTenants`, `AzureGraph/WebApi/ClaimConnectorConfigurations` (User `src/UserService.Data/V2/Database/ServiceDbContext.cs`); runtime engine is the shared `DIT.Connectors.*` NuGet package, not in the repo (User `docs/context.md`) | later | The target replaces the connector engine with one fixed Tenant Middleware contract. Rebuild connectors only if tenants need heterogeneous sources |
| Tenant connector secrets | `Mini.UserService` config rows for WebApi | `AzureGraphConnectorConfiguration.ClientSecret` is a column in the User database (User `src/UserService.Data/V2/Models/AzureGraphConnectorConfiguration.cs`) | never | Secrets must live in a secret store, not in a table (see section 7) |
| Tenant mismatch on repeated authorize | None | `EquisoftAuthorizeInteractionResponseGenerator` forces `login_required` when `acr_values` tenant differs from the session's tenant claim, with a `LinkedTenants` exception list (IdG `IdentityServer/ResponseHandling/EquisoftAuthorizeInteractionResponseGenerator.cs`) | later | Only relevant with several tenants per session. With one tenant per user in v1 it is not needed |
| Tenant on a service token | Parsed from `client_id` suffix `{id}.{tenant}` (`Mini.Infrastructure/Identity/IdentityContext.cs`) | Explicit `service_tenant` / `service_tenantId` claims (IdG `Data/Externals/Clients/UserClient.cs`) | now | Prefer an explicit claim. Mini's suffix convention cannot express "all tenants" (comment in `IdentityServerHost/Configurations/IdentityServerConfig.json`) |

## 4. Service-to-service authentication

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| Identity Server -> User Service (the profile hop) | Self-issued JWT from `IIdentityServerTools.IssueClientJwtAsync`, 300 s, no scope, no `/connect/token` (`IdentityServerHost/ExternalServices/UserClient.cs`) | Same self-issued JWT, 60 s, with `scopes` = audience and claims `service_tenant`, `service_tenantId`, `service_isService` (IdG `Data/Externals/Clients/UserClient.cs`) | now | Target says client credentials with scope `user.read`. Use a registered client and `/connect/token`, so the credential is revocable and auditable. Mini's own comments call this out (`Mini.UserService/Program.cs`, authorization block) |
| User Service -> external callee | Client credentials per tenant: client id `{ClientId}.{tenant}`, secret per tenant, token cached in `IMemoryCache` (`Mini.Infrastructure/ExternalServices/TokenClient.cs`) | `ITokenClient` from the shared DIT library, config `ServiceAccounts:TokenEndpoint`, `PrincipalPrefix`, `TenantSecrets` (User `src/UserService/appsettings.json`, `src/UserService.Data/V2/Repositories/TokenRepository.cs`) | now | Needed for User Service -> Tenant Middleware. Mini shows the pattern, the DIT library implementation is unavailable (see Not read) |
| Inbound token validation | JwtBearer against the IdS discovery/JWKS, `MapInboundClaims = false`, `ValidAudiences` (`Mini.UserService/Program.cs`) | `AddJwt()` from DIT.Auth, config `auth:jwt:authority/audience/issuer/issuers` (User `src/UserService/Startup.cs`, `src/UserService/appsettings.json`) | now | Standard JWT bearer. `MapInboundClaims = false` is a trap worth keeping |
| Scope enforcement | Policies `UserApi` (aud only) and `UserApiManagement` (aud + scope) (`Mini.UserService/Program.cs`) | Controllers use `[Authorize]` only; the management controller adds `ServiceAccountAuthorizeFilter` (User `src/UserService/Infrastructure/Authentication/ServiceAccountAuthorizeFilter.cs`). ACME MW uses policy `scope_read:acmemiddleware` (ACME MW `src/AcmeMiddleware/Startup.cs`) | now | Require both audience and scope `user.read` on the role/group endpoint |
| Distinguishing a service from a user | "No `sub` claim means service" (`Mini.Infrastructure/Identity/IdentityContext.cs`); proved insufficient in Mini | `IIdentityContext.IdentityType` from the DIT library, `service_isService` claim (User `ServiceAccountAuthorizeFilter.cs`) | now | Use an explicit claim or scope, not the absence of `sub` |
| Failure behavior at the profile hop | `UserClient` calls `EnsureSuccessStatusCode()`: failure throws, the login fails (`IdentityServerHost/ExternalServices/UserClient.cs`) | `UserClient.GetRoleAsync` returns null on non-2xx; the caller then throws, the exception is caught and logged and the token is issued without a role: fail open (IdG `Data/Externals/Clients/UserClient.cs`, `EquisoftTokenResponseGenerator.cs`) | now | Decision: fail closed. Take Mini's behavior, not production's. See surprises |
| Failure behavior at tenant lookup | Throws on any non-2xx | Throws on network exception, returns null on non-2xx; null then throws "error while try to get the tenant" (IdG `TenantClient.cs`, `EquisoftTokenResponseGenerator.cs`) | now | Fail closed both ways; also treat a missing or inactive tenant as an error |
| User Service -> Tenant Middleware failure | Connector errors are absorbed by cascading chains; non-cascading handlers surface 502 (`Mini.UserService/Endpoints/UserEndpoints.cs`) | `UserService.GetRoleAsync` returns null when the cascade fails, or retries single path on exception (User `src/UserService.Services/V2/Services/UserService.cs`); controller returns 404 on null | now | Decision: fail closed. A middleware error must surface as an error, not as an empty roles list |
| HTTP resilience | Polly retry (2, exponential) and circuit breaker (3 failures, 30 s) (`Mini.Infrastructure/Http/ResiliencePolicies.cs`) | `AddRetryHandler` / `AddCircuitBreakerHandler` from DIT.HTTP, config `httpClient:transient` (3 retries, 30 s) (IdG `Startup.cs`) | now | Retries are fine if the final outcome is still a refusal. Put in the shared library (Track C) |
| User Service -> Identity Server (reverse call) | Service account per tenant, scope `IdentityServerApi` (`IdentityServerHost/Configurations/IdentityServerConfig.json`) | Same direction exists (User -> IdG convert) | never | Avoid the circular dependency in the rebuild |
| Forwarding the end-user JWT | `Authorization` header on connector calls uses the service token | `.ForwardJwt()` and `UserJWTAccessor` forward the caller's JWT (User `src/UserService/Startup.cs`, ACME MW `src/AcmeMiddleware/Infrastructure/UserJWTAccessor.cs`) | later | Not in the target flow. Revisit if the Tenant Middleware needs end-user context |

## 5. Caching

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| Tenant GUID cache at the Identity Server | `IDistributedCache` in memory, never expires (`IdentityServerHost/Services/SampleProfileService.cs`) | Same, in Redis, never expires (IdG `EquisoftTokenResponseGenerator.cs`; Redis wired in `Configurations/Extensions/CachingExtensions.cs`) | never | Decision: no profile caching at the IdS. A tenant GUID change is never seen without a restart |
| Role cache at the Identity Server | None (stated as deliberate) | None. `UserClient` is not cached (IdG `docs/context.md`) | never | Matches decision |
| Role cache inside the User Service | None | Redis, 1 hour TTL for the Graph service principal and for each user's app-role string; generic Redis default is 7 days (User `docs/context.md`, `src/UserService.Services/V2/Connectors/AzGraph/AzureGraphConnector.cs`) | later | Not needed to meet v1. If added later, define invalidation first, because a 1 hour role cache means a removed role stays valid for up to an hour |
| Service-account token cache | `IMemoryCache` per client id, TTL = lifetime minus 30 s (`Mini.Infrastructure/ExternalServices/TokenClient.cs`) | `IDistributedTokenCache` registered in User (User `src/UserService/Startup.cs`); behavior inside DIT library unverified | now | Caching an outbound client-credentials token is safe and cuts load on the IdS |
| Session and refresh-token linking cache | None | Distributed cache holds a per-session record (external refresh token, SAML session expiry, 20 min sliding) and a refresh-token link, 30 days (IdG `Modules/Account/ExternalController.cs`, `EquisoftTokenResponseGenerator.cs`, `Infrastructure/Cache/CacheManagement.cs`) | later | Used to refresh against the external provider. Not needed for a first demo without refresh tokens |
| Cache backend selection | `AddDistributedMemoryCache` | `UseMemoryCache` flag, else Redis from `persistence:redis:connectionString`, else startup exception (IdG `Configurations/Extensions/CachingExtensions.cs`) | later | Nothing in v1 needs a distributed cache. If added, fail at startup when misconfigured, as production does |
| Authorization decision cache | `DecisionCache` in Mini.AuthorizationService | Unverified | never | Permissions are deferred |

## 7. Extra areas that matter for the rebuild

| Feature | Mini | Production | Include (now/later/never) | Reason |
|---|---|---|---|---|
| Persistence engine | SQL Server; three Identity Server contexts (config, grants, users) in one database; separate `MiniUsers` database for User Service | SQL Server; `persistence:serviceDb`; Duende config/grant stores plus `UserDbContext` (IdG `Startup.cs`); User has its own `ServiceDbContext` (User `src/UserService.Data/V2/Database/ServiceDbContext.cs`) | now | Rebuild uses PostgreSQL. Keep database-per-service. Re-generate migrations; do not port SQL Server specifics such as `NEWSEQUENTIALID()` (Mini uses `Guid.CreateVersion7()`) |
| Migrations | Applied at startup (`Database.Migrate()`) | Opt-in: `persistence:serviceDb:applyMigrations` (default false) plus startup tasks (IdG `appsettings.json`, `Startup.cs`); User: `dotnet run --args runDatabaseMigration` (User `README.md`) | now | Apply by an explicit step, not on every boot of every replica |
| Client / resource configuration | Seeded from `IdentityServerConfig.json` by `Tools/ConfigIngestionTool` into Duende EF tables | `config/*.json` ingested into DB-backed stores; `WildcardRedirectUriValidator`, `WildcardCorsPolicyService` (IdG `config/`, `IdentityServer/`) | now | Needed for the demo client and the User Service client. Skip wildcard redirect/CORS support. Wildcard redirect URIs and CORS wildcards use non-equivalent rules (IdG `docs/context.md`, "Invariants") |
| Duende license | Not handled | Required in Production, startup throws without it (IdG `Startup.cs`, `Configurations/License/*`) | now | Plan for a license key at deployment. Unverified whether the new program already has one |
| Signing keys | `KeyManagement:Provider` = `Developer` (default) or `AzureKeyVault` store (`IdentityServerHost/KeyManagement/*`); Duende automatic key management disabled | `KeyManagementProvider` = Azure Key Vault certificate, local certificate with `Current/Next/Last`, or developer key; startup throws if none (IdG `Configurations/Certificates/*`, `appsettings.json`). Duende `KeyManagement.Enabled = false` | now | A key provider is needed. Decide between Duende automatic key management and an external vault (open question). A developer key must never reach a shared environment |

## ACME.API.Middleware: what it does and what Track M should take

What the code shows (ACME MW `src/AcmeMiddleware/`):

| Aspect | Finding |
|---|---|
| Stated purpose | `appsettings.json` swagger description: "Middleware implementation to test our plugins system and also give a reference implementation." |
| Overall scope | A large insurance-domain reference API (policies, quotes, applications, claims, forms, documents, analytics, calculations, OIPA submission). Controllers are under `V1/Controllers/` |
| Identity-relevant part | `V1/Controllers/UserController.cs` only. Routes: `PUT api/v1/User/{statusCode}/updateUserEmail` (returns random status), `GET api/v1/User/identities/role/{userId}`, `POST api/v1/User/identities`, `GET api/v1/User/identities/email` |
| How it finds a user's role | `Services/UserService.cs`: calls Microsoft Graph `Users[id].MemberOf`, keeps the display names of Entra groups, sorts them and returns the first as the "role" (logs a warning when several) |
| How it returns user info | Graph directory lookup returning `UserId`, `FirstName`, `LastName`, `Email` from the `emailAddress` sign-in identity |
| Auth | JWT bearer (`auth:jwt:audience` = `middlewareapi`), policy `scope_read:acmemiddleware` (`HasScopeRequirement`) on each user route; also cookie + OIDC client `middlewareapi.Guest.ACME` with `acr_values=tenant:ACME` hard-coded in `Startup.cs` |
| Tenant | There is no tenant resolution in the user routes. The tenant `ACME` is hard-coded in `Startup.cs` and `appsettings.json` (`ServiceAccounts:TenantSecrets:ACME`). No endpoint returns a tenant |
| Relationship to the rest | It is the kind of target a User Service WebApi connector calls: same four route shapes as User's `UserController`. Mini's counterpart is `Mini.AcmeApi` (`/users/{userId}`, `/users/by-email/{email}`) |
| Runtime | net8.0, built with the shared DIT packages, CI via Azure DevOps (`azure-pipelines.yml`) |

Important: the task background says its role is to return tenant, user identity and groups. In the code read it does not return a tenant, and it returns a single group-derived role string, not a list of groups. See the surprises section.

What Track M should take from it (later, not this phase):

| Take | Why |
|---|---|
| The idea of a tenant-side service that translates "who is this user in the tenant's own directory" into role and group names | It is the one production example of a tenant-owned source (Entra group membership via Graph) |
| The route shapes `identities/role/{userId}` and `identities/email` as a compatibility reference | Existing connectors target these routes. The new contract can differ, but a mapping is needed |
| Scope-based protection (`scope_read:<api>`) plus a service-account client per tenant | Matches the new decision of scope `user.read` |
| Not the fixed role strings in `V1/Models/Constants/IdentityConstant.cs`, nor "first alphabetical group wins" | Both lose information and are domain-specific |
| Not the Graph filter built with string concatenation in `GetUserByEmailAsync` (it embeds a hard-coded issuer domain) | Injection risk and a hard-coded dev tenant domain |
| An explicit tenant on the contract | Production never returns it from this API, so Track M must define it |

## Surprises and open questions for the owner

Surprises (facts found in the code):

1. **Production fails open on the role hop, Mini fails closed.** IdG catches the exception in `AddIdentityRoleToPayloadAsync`, logs it and issues a token without the role (IdG `src/Equisoft.IdentityGateway/IdentityServer/ResponseHandling/EquisoftTokenResponseGenerator.cs`). Mini throws and the login fails. IdG's own `docs/context.md` flags that it was not confirmed whether a User Service outage blocks login. The code read says it does not.
2. **Production tenant lookup mixes both behaviors.** Network exception throws, non-2xx returns null (then also throws in the generator). The never-expiring cache means a bad tenant GUID is stuck until restart.
3. **Production auto-provisions every unknown external user.** There is no allow-list (IdG `docs/context.md`). The new decision (refuse unknown users) reverses this, so every existing tenant onboarding step needs a pre-registration path.
4. **Production claim names differ from the target.** Role is `identityRole`, tenant GUID is `tenantId`, tenant key is `tenant`. Consumers of the existing tokens will not see `role`, `group` or a single `tenant` claim.
5. **No group concept exists in IdG or User.** The only group use is in ACME MW, collapsed into one "role" string. Groups are new design work, not a port.
6. **ACME.API.Middleware does not do what the brief says.** It is a mock/reference insurance API with a small user controller. It does not return tenant, and it returns one role, not groups. Track M may need a new contract, not an adaptation.
7. **Secrets in source.** `config/identityProviders.json` in IdG holds client secrets that look real (not reproduced here). User stores the Azure Graph `ClientSecret` in a database column. ACME MW `appsettings.json` has a hard-coded Application Insights instrumentation key. Worth a security review independent of this program.
8. **Random display name.** IdG picks one of several name claims at random (`new Random()`), so a user's name can change between logins (IdG `docs/context.md`).
9. **User Service has no durable user or role store.** It derives roles from tenant connectors on every call (User `docs/context.md`). The new design (User Service owns roles) is a real change in ownership, not a cleanup.
10. **User Service cascading fallback is narrower than it looks.** The single-connector path is used only when the cascade throws, not when it returns nothing (User `docs/context.md`, "Invariants"). A tenant configured in only one of two tables gets no role.
11. **Versions differ.** IdG is net8.0 on Duende 7.3.2; Mini and User are net10.0, Mini is on Duende 8.0.6. Behavior differences between Duende 7 and 8 were not checked.

Open questions for the owner:

1. Where does the user record live: Identity Server database (as in IdG and Mini) or User Service? Target flow says the IdS calls the User Service for roles, so who stores the (provider, provider user ID) mapping?
2. For "unknown users refused": how are users registered before first login (admin API, bulk import, invitation)? Who may register a user in a tenant?
3. `tenant` claim value: friendly key or GUID? Production issues both, Mini issues both.
4. Which Entra ID claim is the "provider's stable user ID": `sub` (pairwise per app) or `oid`? Production maps `oid` to `externalobjectidentifier` when present.
5. Who owns the tenant registry in the new platform: the Tenant Middleware, the User Service, or a separate service? Both User and IdG explicitly do not own it today.
6. Should the User Service return groups straight from the Tenant Middleware, or filter/rename them? Are group names unique across tenants?
7. Failure semantics when the Tenant Middleware answers but returns no groups for a valid user: empty list allowed, or refusal?
8. Key management: use Duende automatic key management, or an external vault as production does (`KeyManagement.Enabled = false`)? Which vault technology on the target platform?
9. Duende license: is one available for the new environments? IdG throws at startup in Production without it.
10. Does the demo need refresh tokens or sessions longer than an access token? Production's refresh handling links external provider tokens through a distributed cache.
11. Is it acceptable that the existing production role vocabulary (`Agent`, `ManagingAgent`, `Client`, `Employee`, `Guest`) is not carried over?
